## 0. Rules for the coding agent (read first)

1. **Build from scratch.** This is a 24-hour hackathon (Anvathon, NIE Mysuru, 30-31 Oct 2026). Do not copy code from any older project. Start from an empty repo.
2. **Never invent hospital data.** Hospital names, phone numbers, coordinates and capabilities must come only from `data/hospitals.json`, which the human team fills in and verifies by hand. If the file has only fixtures, use them and keep the `"verified": false` flag visible in the code. Do not generate "realistic" hospitals to fill gaps.
3. **Never give medical advice.** The app helps choose a hospital. It does not diagnose, name drugs, or tell users how to treat anyone. See section 9.
4. **Keep LLM calls to a minimum.** At most one LLM call per user query, with a keyword fast path before it and a rule-based fallback after it. The team has been blocked by API rate limits before. See section 7.
5. **MVP first.** Finish everything in section 11 (MVP) before touching anything in section 12 (stretch).
6. **Work in small steps.** After each milestone in section 13, make sure `npm run dev` and the API both start, commit, then continue. Do not rewrite working parts without being asked.
7. **Ask before assuming** anything that changes scope, data schema or the API contract. Otherwise follow this document.
8. Keep code simple and readable. Four students will edit it during the event. Prefer plain functions, typed schemas and short comments over clever abstractions.

## 1. One-line pitch

> In a medical emergency, people go to the nearest hospital, not the one that can actually treat them. SahayAI takes a plain-language description of the emergency, works out what kind of care is needed, and gives a straight answer: the nearest hospital that is equipped for exactly this situation, with a route and a ready-to-send pre-alert.

## 2. Problem statement

**Title:** Right Hospital, First Time: AI-Based Emergency Care Matching

In an emergency, people lose critical minutes going to a hospital that cannot treat their situation: wrong turns, transfers, and phone searches. Travellers and young people in an unfamiliar city usually do not know which hospital handles poisoning, burns, snake bites or cardiac cases. Ambulances can be delayed, and many people already take patients by auto or cab. Existing hospital finders show what is nearby, but they cannot tell which hospital is equipped for this specific emergency.

**Example scenario (use for the demo):** A young man in a hotel in a new city has accidentally swallowed acid. His friends do not know which nearby hospital has emergency and ICU care for poisoning. They type "my friend drank acid, he is 19, he is conscious but in pain". The app shows a Call 108 button first, then a single recommended hospital that is 24x7 and has poison/ICU capability, with distance, estimated travel time, the reasons for the pick, a live route, and a pre-alert message they can send or read to the hospital.

## 3. Goals and non-goals

**Goals**
- Turn free-text (English, Hindi, Kannada, mixed) into a structured emergency classification.
- Recommend hospitals by **capability match first, distance second**.
- Give a clear, single answer within a few seconds, with two backups.
- Always put "Call 108" first and make the safety limits obvious.
- Run the whole demo reliably even if the LLM API fails or the network is poor.

**Non-goals (do not build)**
- Diagnosis, triage scoring for clinicians, treatment or first-aid instructions generated by AI.
- Live bed or ICU availability (we cannot get this data and must not pretend to).
- User accounts, login, payments, ambulance booking, hospital-side dashboards.
- Coverage outside Mysuru for the demo (the method scales by extending the dataset; say so in the pitch).

## 4. Users

- A panicked bystander or friend typing quickly on a phone.
- Travellers and students in a city they do not know.
- Usage is one-handed, stressed and possibly low-bandwidth. The UI must be large, fast and simple.

## 5. Core user flow

1. User opens the app. The top of the screen shows **Call 108 (ambulance)** and **112** buttons.
2. The browser asks for location permission. If denied or unavailable, show a manual area picker (a dropdown of a few Mysuru localities with coordinates) and a clear note that results are approximate.
3. User types the situation (or taps an example chip) and presses **Find the right hospital**.
4. Backend classifies the emergency (keyword fast path, otherwise one LLM call, otherwise fallback).
5. Backend filters and ranks hospitals (section 8) and returns the result.
6. UI shows:
   - Red banner if red flags are present (unconscious, not breathing, severe bleeding, seizure): "Call 108 now."
   - **Top pick card:** hospital name, distance, estimated travel time, why it was chosen, matched capabilities, **Navigate**, **Call hospital**, **Copy pre-alert**.
   - **Two backups** in smaller cards.
   - Note: "If an ambulance is delayed or the patient is getting worse, go now rather than waiting."
   - Footer disclaimer (section 9).

## 7. Emergency classification

### 7.1 Taxonomy (`data/emergency_types.json`)

Each type has `required` capabilities (hard filter) and `preferred` capabilities (used for ranking).

| type | required | preferred |
|---|---|---|
| poisoning_ingestion | emergency_24x7, icu | toxicology_poison, picu (if child) |
| burns | emergency_24x7 | burns_unit, icu, plastic_surgery |
| snake_bite | emergency_24x7, anti_venom, icu | ventilator |
| cardiac | emergency_24x7, icu | cardiac_cath_lab, cardiology |
| stroke | emergency_24x7, ct_scan | stroke_unit, neurology, icu |
| trauma_accident | emergency_24x7, ct_scan, blood_bank | trauma_center, orthopaedics, neurosurgery, icu |
| severe_bleeding | emergency_24x7, blood_bank | trauma_center, icu |
| obstetric | emergency_24x7, obstetrics | nicu, blood_bank |
| pediatric_emergency | emergency_24x7, paediatrics | picu, nicu |
| breathing_difficulty | emergency_24x7, icu | ventilator, pulmonology |
| seizure | emergency_24x7 | neurology, icu, ct_scan |
| allergic_reaction | emergency_24x7 | icu |
| electric_shock_drowning | emergency_24x7, icu | ventilator |
| minor_injury_fracture | emergency_24x7 | orthopaedics |
| general_unclear | emergency_24x7 | icu |

Rule: if `age_group` is `child`, add `paediatrics` to preferred (and `picu` if severity is critical or serious).

### 7.2 Classifier output (Pydantic model, strict JSON)

```json
{
  "type": "poisoning_ingestion",
  "severity": "critical | serious | moderate | unclear",
  "age_group": "child | teen | adult | elderly | unknown",
  "red_flags": ["unconscious", "not_breathing", "severe_bleeding", "seizure", "chest_pain"],
  "summary": "one-line English summary of the situation",
  "confidence": 0.0,
  "input_language": "en | hi | kn | mixed"
}
```

### 7.3 Three-stage pipeline (in this order)

1. **Keyword fast path** (no API call). A dictionary of keywords per type in English, Hindi (Devanagari and Roman), and Kannada (script and Roman). Examples: acid, poison, drank, swallowed, vish, vishha; burn, fire, jal gaya, suttu; snake, saap, havu; chest pain, heart attack, seene mein dard; accident, crash, fell from; pregnant, labour, delivery; fits, seizure; not breathing, unconscious, behosh. If one type clearly matches, return it with `classifier: "keyword"` and skip the LLM. Also extract red flags and age hints with keywords.
2. **LLM call (only if the fast path is unsure).** One call, strict JSON schema, temperature 0, 6-second timeout. Provider order: Gemini, Groq, local Ollama (optional). When using Ollama, pass the JSON schema in the `format` parameter. System prompt rules: classify only, do not give advice, do not explain, output JSON only, choose `general_unclear` if unsure.
3. **Fallback (no API).** If all providers fail or time out, return `general_unclear` with `classifier: "fallback"` and a UI warning: "We could not understand the situation fully. Showing the nearest 24x7 emergency hospitals. Call 108."

**Cache:** normalize the text (lowercase, trim, collapse spaces) and cache the classification in memory. Pre-warm the cache with all demo phrases at startup.

**Rate-limit protection:** never call an LLM more than once per request, never retry in a loop (one retry max with a short delay), and log which classifier answered.

## 8. Hospital data and ranking

### 8.1 Hospital schema (`data/hospitals.json`)

```json
{
  "id": "hosp_001",
  "name": "string",
  "lat": 0.0,
  "lng": 0.0,
  "address": "string",
  "phone": "string",
  "type": "government | private | trust",
  "capabilities": ["emergency_24x7", "icu", "ct_scan", "blood_bank"],
  "last_verified": "YYYY-MM-DD",
  "verified_by": "teammate name",
  "source": "phone call | website URL",
  "verified": true,
  "notes": ""
}
```

**Capability tags (fixed vocabulary):** `emergency_24x7`, `icu`, `picu`, `nicu`, `paediatrics`, `obstetrics`, `burns_unit`, `plastic_surgery`, `trauma_center`, `orthopaedics`, `neurosurgery`, `neurology`, `stroke_unit`, `cardiology`, `cardiac_cath_lab`, `ct_scan`, `blood_bank`, `ventilator`, `anti_venom`, `toxicology_poison`, `pulmonology`.

**Fixtures:** until the team supplies real data, create 5 to 6 entries named `SAMPLE HOSPITAL A`, `SAMPLE HOSPITAL B`, and so on, with coordinates scattered within a few kilometres of Mysuru city centre (about 12.2958 N, 76.6394 E), and `"verified": false`. The UI must show a small "sample data" badge for any hospital where `verified` is false. Never use real hospital names in fixtures.

**Production mode:** an env flag `ONLY_VERIFIED=true` makes the backend ignore unverified hospitals.

### 8.2 Ranking algorithm (`ranking.py`)

1. Compute haversine distance (km) from the user to every hospital.
2. Remove hospitals farther than 30 km.
3. Split into two groups: those that satisfy **all required** capabilities for the emergency type, and the rest.
4. Within the qualifying group compute a score:
   - `preferred_fraction` = matched preferred capabilities / total preferred (1.0 if none).
   - `distance_score` = `max(0, 1 - distance_km / 25)`.
   - Weights by severity: `critical` uses capability 0.4 and distance 0.6, everything else uses capability 0.6 and distance 0.4.
   - `score = w_cap * preferred_fraction + w_dist * distance_score`.
5. Sort by score descending. Return the top 1 as `recommendation`, the next 2 as `alternatives`.
6. **If no hospital meets all required capabilities:** return the nearest 24x7 emergency hospitals instead, and add the warning: "No verified hospital in our data matches every requirement for this situation. Call the hospital before travelling."
7. Estimated travel time = `distance_km / 25 km/h * 60` minutes (rough city average). Label it "approx." in the UI. Do not call it a live ETA.
8. `reasons` for each hospital are generated from code (not the LLM): e.g. "24x7 emergency", "ICU available", "poison treatment unit", "4.2 km away".

### 8.3 Wording rules
- Say "most suitable based on capability and distance". Never "best hospital".
- Always show `last_verified` in small text on the card.

## 9. Safety requirements (must-have, not optional)

- **Call 108 / 112 buttons** (`tel:` links) are always visible at the top, above the input box, and are the first element on the results page.
- **No treatment advice, no diagnosis, no medicine names, no first-aid steps generated by AI.** If a first-aid section is ever added (stretch only), it must be static text reviewed by a qualified person and clearly labelled.
- **Red-flag escalation:** if the classifier returns any red flag (`unconscious`, `not_breathing`, `severe_bleeding`, `seizure`, `chest_pain`), show a high-visibility banner: "This sounds life-threatening. Call 108 now."
- **Do not tell users to skip the ambulance.** The message is: "Call 108 first. If an ambulance is delayed or the patient is getting worse, go to the hospital now."
- **Disclaimer (footer, always visible on results):** "SahayAI helps you choose a suitable hospital. It does not diagnose or give medical advice. Hospital information is hand-verified by our team and may change. Call the hospital if you can. In an emergency, call 108."
- **Call ahead:** every hospital card has a **Call hospital** button.
- **Honest data:** show `last_verified`. Never claim bed or ICU availability.
- Log nothing personal. Do not store user text or location server-side beyond in-memory caching of normalized text.

## 10. API contract

### `POST /api/triage`

Request:
```json
{ "text": "my friend drank acid, he is 19 and conscious", "lat": 12.2958, "lng": 76.6394, "location_source": "gps | manual" }
```

Response:
```json
{
  "emergency": { "type": "...", "severity": "...", "age_group": "...", "red_flags": [], "summary": "...", "confidence": 0.0, "input_language": "en" },
  "recommendation": {
    "hospital": { "id": "...", "name": "...", "phone": "...", "address": "...", "lat": 0, "lng": 0, "verified": true, "last_verified": "..." },
    "distance_km": 0.0,
    "eta_min_approx": 0,
    "reasons": ["24x7 emergency", "ICU", "poison treatment unit", "4.2 km away"],
    "matched_required": [],
    "matched_preferred": [],
    "missing_preferred": [],
    "directions_url": "https://www.google.com/maps/dir/?api=1&origin=LAT,LNG&destination=LAT,LNG&travelmode=driving",
    "call_url": "tel:+91..."
  },
  "alternatives": [ { "...same shape as recommendation..." } ],
  "pre_alert_text": "Patient: young male (about 19). Situation: swallowed acid, conscious, in pain. Arriving by private vehicle in about 15 min. Please be ready.",
  "emergency_numbers": { "ambulance": "108", "unified": "112" },
  "warnings": [],
  "meta": { "classifier": "keyword | llm | fallback", "provider": "gemini | groq | ollama | none", "latency_ms": 0, "cached": false }
}
```

### Other routes
- `GET /api/health` returns `{ "status": "ok", "hospitals_loaded": n, "verified_count": n }`.
- `GET /api/hospitals` returns the loaded dataset (for debugging and a stretch map view).

CORS: allow the frontend origin from an env var. Validate lat/lng ranges and cap `text` at 500 characters.

### Pre-alert template (`prealert.py`)
Built from code, not the LLM:
```
EMERGENCY PRE-ALERT (via SahayAI)
Patient: {age_group_phrase}
Situation: {summary}
Condition flags: {red_flags or "none reported"}
Coming from: {distance_km} km away, arriving in about {eta_min} min by private vehicle
Contact: [caller to add phone number]
Please be ready. Details are user-reported and unverified.
```
